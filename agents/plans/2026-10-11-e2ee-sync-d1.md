# Encrypted sync service on the existing Cloudflare worker

## Context

Techo's readable journal (to-dos, posts, notes) currently lives in per-user Turso databases. A leak of the Turso group token exposes that text. The target is the Obsidian Sync shape: each device holds plaintext SQLite, and the server stores an append-only log of ciphertext plus a wrapped data key.

Constraints:

- The existing Turso API, auth, and calendar sync keep serving the desktop and mobile apps.
- The only application server stays the Hono worker on Cloudflare (`api.techoo.app`).
- There is no production journal to migrate into the new log.
- Cloudflare D1 is the store for the new log. KV is the wrong shape: the log needs a monotonic sequence, a unique `client_op_id`, and `seq > cursor` reads.

## Decision

Add a second data plane on the same worker. Domain routes keep using Turso. New routes use a D1 binding named `SYNC_DB`:

| Method | Path | Role |
|---|---|---|
| `PUT` | `/api/v1/vault` | Store the wrapped data key. One active vault per user. |
| `GET` | `/api/v1/vault` | Return the wrapped key and the chain head. |
| `POST` | `/api/v1/vault/reset` | Retire the vault, delete its ops, store a new wrapped key. |
| `GET` | `/api/v1/sync` | Return `vaultId`, `headSeq`, `headHash`. |
| `POST` | `/api/v1/sync/ops` | Append ciphertext snapshots. |
| `GET` | `/api/v1/sync/ops` | Pull ops with `seq` greater than `after`. |

The worker checks the JWT, assigns `seq`, and stores bytes. It does not decrypt. The hash chain is SHA-256 over `prevHash|seq|recordId|ciphertext`. A lost append race rolls the D1 batch back via a `head_seq` compare that divides by zero when the head moved, then the request retries.

D1 sessions use `first-primary` so the cursor is not read from a stale replica.

Account deletion also deletes that user's D1 rows when the binding is present. If D1 is not configured yet, account deletion still completes.

Schema lives in `apps/backend/sync-migrations/`, separate from the Turso Drizzle migrations.

Before the sync routes do anything in production, create the database and add the binding under `env.prod` in `wrangler.jsonc` (that key is not inherited from the top level):

```sh
pnpm --filter @apps/backend exec wrangler d1 create techoo-sync
```

Paste the returned `database_id` into `env.prod.d1_databases`, then:

```sh
pnpm --filter @apps/backend run d1:migrate:prod
```

Until that binding exists, production deploys do not include D1. The new routes answer `503 sync_unavailable`. Existing Turso routes do not touch D1.

## End-to-end tests

The sync service is proven through the HTTP stack it will serve: JWT verification, the vault and sync routes, and the handlers. The store is the in-memory libSQL database that applies `sync-migrations/0001_init.sql`. The suite does not open Turso, does not need a Cloudflare account, and does not listen on a port.

`apps/backend/scripts/e2e.ts` stays a separate live-server script. It signs up through Better Auth, which needs the Turso env, and the sync routes answer `503` until `SYNC_DB` exists. That script is not this suite.

File: `apps/backend/src/app/api/[[...route]]/handlers/sync.e2e.test.ts`. `pnpm --filter @apps/backend run test` includes it with the other `*.test.ts` files.

Harness:

- `vi.hoisted` sets `JWT_SECRET` and `BETTER_AUTH_URL` before `jwt.ts` caches them. No Turso or Google variables are set.
- The app is an `OpenAPIHono` mounted at `/api`. It sets a silent logger and the memory `syncDb`, then `registerJwtAuthMiddleware`, then the six vault and sync routes.
- It does not call `createApp()` from `route.ts`. That startup path runs `validateEnv()` and requires the full Turso and Google configuration.
- The test does not preset `c.set('user')`. `signJwt` issues the bearer token and the middleware calls `verifyJwt`. A device is that account token plus the `deviceId` on each op. Two devices of one account are two tokens with the same `sub` and different `deviceId` values.
- Paths are `/api/v1/vault` and `/api/v1/sync`, so `isEncryptedSyncPath` matches. The tenant-database and OAuth factories throw if the middleware calls them. A route that leaves the encrypted-sync allowlist fails the suite instead of dialing Turso.
- Handler unit tests in `sync.test.ts` still preset the user and skip JWT. `jwt-auth.sync.test.ts` still mocks `verifyJwt`. This file is the one that joins those two layers.

Cases:

1. A missing bearer token, and a bearer token signed with the wrong secret, return `401`. No vault or op row is written.
2. Device A `PUT /api/v1/vault` returns `201`. `GET /api/v1/vault` and `GET /api/v1/sync` return `headSeq` 0 and `headHash` equal to the genesis hash (64 zero hex characters).
3. Device A pushes two ciphertext ops. The first `prevHash` is the genesis hash. The second is `SHA-256(prevHash|seq|recordId|ciphertext)` of the first. `GET /api/v1/sync` `headHash` equals that chain. Pull `after=0` returns both ciphertexts unchanged. Pull `after=1` returns only the second.
4. Pushing the same `clientOpId` again returns the original `seq`. `headSeq` does not advance.
5. Device B, same account and a different `deviceId`, appends one op. Device A pulls `after` its previous head and receives only that op, with Device B's `deviceId` and the same ciphertext.
6. After a push, `POST /api/v1/vault/reset` returns a new `vaultId` and `headSeq` 0. Push and pull with the retired id return `409` `vault_reset`. Pull on the new id returns no ops, so the previous ciphertext is gone.
7. A second account's JWT `GET /api/v1/vault` returns `404` `vault_not_found`. Pull with the first account's `vaultId` returns `404`.
8. One batch that repeats `clientOpId` returns `400` `duplicate_client_op` and writes nothing.
9. A valid JWT with a non-UUID `vaultId` returns `400` from request validation. The bearer check runs first, so the same body without a token is `401`.

Passphrase derivation, AES-GCM, and the on-device SQLite merge stay on the client. This suite checks that the server stores and returns ciphertext and that the hash chain a client can recompute matches the head.

## Consequences

- Clients do not read the journal from these routes yet. Local SQLite and device sync come later.
- A note ciphertext must stay under D1's 2 MB row limit. The API rejects a ciphertext string longer than 1,000,000 characters.
- The server can see record ids, device ids, and when an op was stored. It cannot see the fields inside the ciphertext.
- Production keeps deploying without D1. The sync routes start storing data only after the `env.prod` binding is filled in.
- JWT middleware verifies the bearer token for these routes and does not open a Turso tenant database. Domain routes still do.
