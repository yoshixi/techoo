# Encrypted sync service on the existing Cloudflare worker

## Context

Techo's readable journal (to-dos, posts, notes) currently lives in per-user Turso databases. A leak of the Turso group token exposes that text. The target is the Obsidian Sync shape: each device holds plaintext SQLite, and the server stores an append-only log of ciphertext plus a wrapped data key.

Constraints:

- The existing Turso API, auth, and calendar sync keep serving the desktop and mobile apps.
- The only application server stays the Hono worker on Cloudflare (`api.techoo.app`).
- There is no production journal to migrate into the new log.
- Cloudflare D1 is the store for the new log. KV is the wrong shape: the log needs a monotonic sequence, a unique `client_op_id`, and `seq > cursor` reads.

## Decision

Add a second data plane on the same worker. Domain routes keep using Turso. New routes use a D1 binding named `SYNC_DB`:

| Method | Path | Role |
|---|---|---|
| `PUT` | `/api/v1/vault` | Store the wrapped data key. One active vault per user. |
| `GET` | `/api/v1/vault` | Return the wrapped key and the chain head. |
| `POST` | `/api/v1/vault/reset` | Retire the vault, delete its ops, store a new wrapped key. |
| `GET` | `/api/v1/sync` | Return `vaultId`, `headSeq`, `headHash`. |
| `POST` | `/api/v1/sync/ops` | Append ciphertext snapshots. |
| `GET` | `/api/v1/sync/ops` | Pull ops with `seq` greater than `after`. |

The worker checks the JWT, assigns `seq`, and stores bytes. It does not decrypt. The hash chain is SHA-256 over `prevHash|seq|recordId|ciphertext`. A lost append race rolls the D1 batch back via a `head_seq` compare that divides by zero when the head moved, then the request retries.

D1 sessions use `first-primary` so the cursor is not read from a stale replica.

Account deletion also deletes that user's D1 rows when the binding is present. If D1 is not configured yet, account deletion still completes.

Schema lives in `apps/backend/sync-migrations/`, separate from the Turso Drizzle migrations.

Before the sync routes do anything in production, create the database and add the binding under `env.prod` in `wrangler.jsonc` (that key is not inherited from the top level):

```sh
pnpm --filter @apps/backend exec wrangler d1 create techoo-sync
```

Paste the returned `database_id` into `env.prod.d1_databases`, then:

```sh
pnpm --filter @apps/backend run d1:migrate:prod
```

Until that binding exists, production deploys do not include D1. The new routes answer `503 sync_unavailable`. Existing Turso routes do not touch D1.

## Consequences

- Clients do not read the journal from these routes yet. Local SQLite and device sync come later.
- A note ciphertext must stay under D1's 2 MB row limit. The API rejects a ciphertext string longer than 1,000,000 characters.
- The server can see record ids, device ids, and when an op was stored. It cannot see the fields inside the ciphertext.
- Production keeps deploying without D1. The sync routes start storing data only after the `env.prod` binding is filled in.
- JWT middleware still resolves the Turso tenant client for these routes, the same as every other authenticated route. That lookup is unused by the sync handlers.
